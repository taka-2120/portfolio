# ポートフォリオに Next.js を選んだ理由

個人ポートフォリオを作るときは、流行りのスタックではなく自分に合ったものを選ぶ絶好の機会です。**Next.js 16（App Router）** に決めるまでの経緯をまとめます。

## 要件の整理

フレームワークを選ぶ前に、本当に必要なものをリストアップしました。

- **静的生成** — 動的データがないので CDN フレンドリーな出力が理想
- **バイリンガル対応（英語・日本語）** — ルートにロケール情報を持たせたい、ボイラープレートは最小限に
- **MDX** — コンテンツは Markdown で書きたい、JSX にハードコードしたくない
- **TypeScript サポート** — 型エラーは本番ではなくビルド時に検出したい

Next.js はすべてを満たしていました。

## App Router と i18n

`[lang]` 動的セグメントを使うアプローチはシンプルです。すべてのページは `src/app/[lang]/` 以下に置き、`generateStaticParams` でビルド時に両ロケールを静的生成します。

```ts
export async function generateStaticParams() {
    return [{ lang: "en" }, { lang: "ja" }];
}
```

辞書ファイル（`public/dictionaries/en.json`、`ja.json`）はサーバーサイドで読み込むため、ロケール処理がクライアントバンドルに含まれません。

## MDX ページのために Nextra を採用

[Nextra](https://nextra.site) は Next.js を MDX に特化した形でラップするフレームワークです。経歴ページやアプリ詳細ページのように MDX で書きたいコンテンツには Nextra がレンダリングを担ってくれるため、remark/rehype の設定を手動で組む手間を省けました。

## 今ならどう選ぶか

今から始めるなら **Astro** ももっと真剣に検討すると思います。ほぼ静的なバイリンガルサイトであれば、Astro のアイランドアーキテクチャはデフォルトで送るJavaScriptが少なくなる可能性があります。ただし、React エコシステムに慣れていること、サイトが今後成長する可能性を考えると、Next.js のほうが長期的に安心できる選択肢だと感じています。

## まとめ

Next.js が常に正解というわけではありませんが、静的生成・MDX・堅牢な TypeScript を求める React 開発者にとっては、なかなか代え難い選択肢です。
